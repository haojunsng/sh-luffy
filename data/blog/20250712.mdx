I’ve always been curious about how subscription features work under the hood — specifically how emails are captured, how notifications are sent, and how unsubscribe links function (_because honestly, sometimes I can't seeem to unsubscribe to certain newsletters/sites and it really bugs me_).

With a blog of my own now, I figured it was the perfect opportunity to finally scratch this itch.

I thought a great way to do a walkthrough of what I've done is by framing it around the three key backend API endpoints powering my subscription system.

## Why I used Cloudflare Workers

First glance on the architecture diagram above might have gotten you wondering why I bothered with Cloudflare Workers when I already have a Next.js backend.

1. **Separation of Concerns**. This was the initial thought - I wanted to keep things clean.

- Frontend handles user input, captcha and UI feedback.
- Backend verifies CAPTCHA, injects secrets and acts as a gateway.
- Cloudflare Worker will then be responsible solely for interfacing with KV.

2. **Lack of Research**. While I was implementing `/subscribe` and `/unsubscribe`, I did not know I could access KV directly from a Next.js project hosted on Pages (_more on this later_), if I wanted to make use of the binding.
   Indeed, I could have ditched the binding and make API calls - but this also came with a set of authentication-related considerations.

Looking back, would I have skipped the Workers and let my backend handle everything? _Maybe_. But in the end, I do think something valuable came out of this possibly over-engineered architecture (_for a hobbyist's blog_) - specifically around the boundaries between frontend, backend and edge.

The first step was capturing the email addresses of people who wanted to subscribe.

Here’s how I designed it:

1. **Cloudflare Worker as the Mini API**:

I provisioned yet another Cloudflare Worker to handle the actual storage (_and removal, as you'd see later_) of subscriber emails. This Worker is protected by a secret token and writes email addresses into a Cloudflare KV store.

2. **Next.js Backend API for Token Protection**:

Since I couldn’t expose my secret token to the frontend client - using component (SubscriptionForm), I built a Next.js backend API endpoint. The subscription form on the client calls this endpoint, which then safely passes the request along to the Cloudflare Worker.

3. **Bot Protection with CAPTCHA**:

<div className="my-8 flex justify-center">
  <img
    src="/static/images/diagrams/captcha.jpg"
    alt="CAPTCHA"
    className="h-auto max-w-full rounded-lg shadow-lg"

As a client-using component, my understanding is that I could not pass any secret tokens to make the request to my endpoint. To prevent bots and spam, this meant that I had to wrap the subscription form with Google reCAPTCHA. Any requests to the backend without a valid CAPTCHA token get rejected immediately.

In short:

**Next.js Frontend ➡️ Next.js Backend API ➡️ Cloudflare Worker ➡️ KV Store**.

Next came the need to notify subscribers whenever a new post is published.

1. **Choosing an Email Provider**:

After a bit of research, I chose Resend as my email provider. The free tier allows 100 emails/day, which is plenty for my needs. I could also send emails using my own domain (mugiwara@snghaojun.com) - _gotta milk the $12/year fee_.

2. **Building the Notify Endpoint**:

The Next.js notification endpoint uses the Resend API to blast emails to subscribers. This endpoint is naturally also protected by a secret token.

Accessing KV from my `route` was such a pain initially. According to ChatGPT, there was no way for me to access because I was using Pages instead of Workers. I thought it was strange that I could still bind to the KV in my Pages if that were true.

Did some googling and voila - stumbled upon this [page](https://developers.cloudflare.com/pages/framework-guides/nextjs/ssr/bindings/) - that was _last updated on May 13, 2025_.

`@cloudflare/next-on-pages` really saved the day.

3. **Triggering Notifications via GitHub Actions**:

Here’s where the imposter syndrome struck hard. Whatever I did and whatever I am about to describe may come across a bit of an anti-pattern -

I wrote a GitHub Actions workflow that:

- Detects new .mdx blog posts in my repository.

- Extracts the title and summary from the frontmatter using `grep` and `sed`.

- Throws the title and summary to my notification endpoint (with a secret token of course) with this info to trigger the email blast.

It feels wrong - I probably should have stored what I needed on the backend through Next.js and accessed them there, but this works for now... so I'm rolling with it.

In short:

**GitHub Actions ➡️ Next.js Backend API ➡️ Resend API ➡️ Subscriber’s Inbox**.

One of my friends, Edwin, was already asking for this feature before I even launched the system (ok bro).

1. Set up the Next.js backend endpoint to receive unsubscribe requests.

2. It then calls the same Cloudflare Worker, which handles putting the email into the KV store.

3. Just like subscribing, the unsubscribe process flows similarly and I could take advantage of the existing binding between the worker and the KV.

Now every email that goes out includes an easy “Unsubscribe” link — because we all know how annoying it is when companies make that impossible/difficult.

In short:

**Email Link ➡️ Next.js Backend API ➡️ Cloudflare Worker ➡️ KV Store (Cloudflare KV)**.
